CORS 核心机制

多个 Access-Control-Allow-Origin
为什么不会报错？

规范允许 ≠ 浏览器支持，深入理解 CORS 的规范与实现差异

⚡

核心结论

🚫
CORS 规范允许服务器返回多个 Access-Control-Allow-Origin 值，但没有任何浏览器支持此行为。如果服务器尝试这样做，浏览器会直接报错。
⚠️
报错信息：Multiple CORS header Access-Control-Allow-Origin not allowed

记住这个原则：CORS 是浏览器的安全策略，规范只是纸面约定，浏览器实现才是真相。

CORS 规范说了什么？

根据 Fetch 标准（WHATWG）和 W3C CORS 规范，`Access-Control-Allow-Origin` 的语法定义为：

ABNF
# Access-Control-Allow-Origin 语法（Fetch 标准） Access-Control-Allow-Origin = origin-or-null / "*" # 规范允许的值： # 1. 单个 origin： https://example.com # 2. null： null # 3. 通配符： * # ⚠️ 规范从未定义「多个 origin」的表示语法
ℹ️
规范允许：单 origin 值、`null`、或通配符 *。规范没有定义多值的表示语法，但也没有明确禁止「多个头部」的情况。
🌐

浏览器实际做了什么？

尽管规范「模棱两可」，但所有浏览器厂商都选择了同一条路：只支持单值。

为什么浏览器不能支持多值？

❌ CORS 需要明确性

浏览器的安全策略需要二元答案："这个响应允不允许当前 origin?"

如果允许多值，浏览器无法给出确定答案。

❌ 凭证（Credentials）冲突

带凭证请求时，ACAO 必须精确匹配请求 origin，或使用 *（但 * 不能与凭证同用）

多值无法满足这一要求。

❌ 语法歧义

「多个 origin」可以有多种表示方法：逗号分隔？空格分隔？重复头部？

规范没有定义，浏览器无法统一实现。

❌ 安全最小化原则

安全策略应遵循最小权限原则：

只允许明确指定的来源，而非模糊的「某些来源」。多值会扩大攻击面。

正确做法：动态回显 Origin

服务器不应该硬编码多个 origin，而是：检查请求的 Origin 是否在白名单中，如果是，原样返回该 Origin。

✅
动态回显的核心：响应中的 ACAO 值精确匹配请求的 Origin，而非硬编码列表。浏览器看到「你是谁，我就信任谁」，而非「我信任的是这些人」。
⌨️

代码示例

Node.js / Express

JavaScript
const allowedOrigins = [ "https://a.com", "https://b.com", "https://c.com" ]; app.use((req, res, next) => { const origin = req.headers.origin; if (allowedOrigins.includes(origin)) { res.setHeader("Access-Control-Allow-Origin", origin); res.setHeader("Access-Control-Allow-Credentials", "true"); res.setHeader("Access-Control-Allow-Methods", "GET, POST, PUT, DELETE"); res.setHeader("Access-Control-Allow-Headers", "Content-Type, Authorization"); } next(); });

Nginx（使用 map）

Nginx
# http 块中定义 map $http_origin $cors_origin { "~^https://(a|b|c)\.com$" $http_origin; default ""; } server { location /api/ { add_header Access-Control-Allow-Origin $cors_origin; add_header Access-Control-Allow-Credentials "true"; add_header Access-Control-Allow-Methods "GET, POST, PUT, DELETE"; add_header Access-Control-Allow-Headers "Content-Type, Authorization"; } }

Python / Flask

Python
ALLOWED_ORIGINS = [ "https://a.com", "https://b.com", "https://c.com" ] @app.after_request def add_cors_headers(response): origin = request.headers.get("Origin") if origin in ALLOWED_ORIGINS: response.headers["Access-Control-Allow-Origin"] = origin response.headers["Access-Control-Allow-Credentials"] = "true" response.headers["Access-Control-Allow-Methods"] = "GET, POST, PUT, DELETE" response.headers["Access-Control-Allow-Headers"] = "Content-Type, Authorization" return response

常见错误配置

❌ Nginx 配置逗号分隔多个 origin

尝试用逗号分隔多个域名，以为这样可以允许多个来源。

浏览器报错
Nginx
add_header Access-Control-Allow-Origin "https://a.com,https://b.com";

❌ 重复设置多个 ACAO 头部

以为设置多个 add_header 行可以「叠加」效果，实际只有最后一个生效。

浏览器报错
Nginx
add_header Access-Control-Allow-Origin "https://a.com"; add_header Access-Control-Allow-Origin "https://b.com";

❌ 同时返回 * 和具体 origin

想同时支持公开访问和特定域名，但带凭证请求时这会导致浏览器拒绝。

浏览器拒绝
Nginx
add_header Access-Control-Allow-Origin "*"; add_header Access-Control-Allow-Origin" "https://a.com";

❌ Express.js 中用 append 添加多个头部

Node.js 的 res.append() 会在已有头部存在时创建多个头部，导致浏览器报错。

浏览器报错
JavaScript
res.append("Access-Control-Allow-Origin", "https://a.com"); res.append("Access-Control-Allow-Origin", "https://b.com"); // 实际产生多个头部 鈫?浏览器报错
⚠️

其他需要注意的场景

⚠️ CDN 多域名配置

CDN 配置面板允许添加多个 origin，但 CDN 对外只返回一个 ACAO。如果 CDN 内部实现产生了多个头部，源站也会收到错误。

配置风险

⚠️ 允许 null origin

如果服务器返回 ACAO: null，会允许来自 file:// 协议、iframe 等的请求，可能导致安全风险。

安全风险

⚠️ CORS 与重定向

跨域重定向后，Origin 可能变为 null 或目标域。需要在重定向目标也正确配置 CORS 头部。

容易遗漏

⚠️ Vary: Origin 头部

使用动态回显时，响应头应包含 Vary: Origin，让缓存正确区分不同来源的响应。
