📊 Cache Mode 对比表
Mode 检查缓存 发送验证 存储响应 缓存未命中 典型场景
default ✅ ✅ 按 HTTP 规则 ✅ 发请求 普通 API 请求
no-store ❌ ❌ ❌ 发请求 实时数据、敏感信息
reload ❌ ❌ ✅ 发请求 强制刷新资源
no-cache ❌ 跳过 ✅ 强制 ✅ 发请求 CDN 缓存但需验证
force-cache ✅ ❌ 不验证 ✅ 发请求 离线优先、不在意过时
only-if-cached ✅ ❌ ❌ ❌ 返回错误 Service Worker 离线策略
💡 关键区别速记
no-cache vs no-store
no-cache = 用缓存但每次验证
no-store = 完全不看也不存
force-cache 风险
缓存命中但过期时，直接返回缓存
不会向服务器验证 — 可能返回过期数据
only-if-cached
必须配合 mode: 'same-origin'
未命中时返回网络错误而非请求
🖥️ 基础代码示例
// 1. default — 遵循 HTTP 缓存规则 const r1 = await fetch('/api/data') // 2. no-store — 完全不碰缓存（实时数据） const r2 = await fetch('/api/stock', { cache: 'no-store' }) // 3. no-cache — 每次都验证缓存有效性 const r3 = await fetch('/api/config', { cache: 'no-cache' }) // 4. force-cache — 有缓存就用，没有才请求 const r4 = await fetch('/static/app.js', { cache: 'force-cache' }) // 5. only-if-cached — 只用缓存（离线场景） try { const r5 = await fetch('/api/data', { cache: 'only-if-cached', mode: 'same-origin' }) } catch (e) { console.log('离线且无缓存') }
🛠️ Service Worker 中的缓存策略
// sw.js — 典型缓存策略组合 self.addEventListener('fetch', (event) => { const url = new URL(event.request.url) // API 请求：网络优先，失败时 fallback 到缓存 if (url.pathname.startsWith('/api/')) { event.respondWith( fetch(event.request, { cache: 'no-store' }) .catch(() => caches.match(event.request)) ) } // 静态资源：缓存优先，验证更新（Stale-While-Revalidate） if (url.pathname.startsWith('/static/')) { event.respondWith( caches.match(event.request).then(cached => fetch(event.request, { cache: 'no-cache' }).then(response => { if (response.ok) { caches.open('static-v1') .then(cache => cache.put(event.request, response.clone())) } return cached || response }) ) ) } })
🌐 模拟服务端条件请求（Node.js）
const http = require('http') const server = http.createServer((req, res) => { const ifNoneMatch = req.headers['if-none-match'] const etag = '"v2-' + Date.now() + '"' // 当客户端带 ETag 发来 no-cache 请求时 if (ifNoneMatch === etag) { res.writeHead(304, { 'ETag': etag }) res.end() // 告诉客户端用缓存 } else { res.writeHead(200, { 'Content-Type': 'application/json', 'ETag': etag, 'Cache-Control': 'max-age=3600' }) res.end(JSON.stringify({ data: 'new content' })) } }) server.listen(3000)
❓ 常见问题解答
Q: fetch 默认会先检查缓存吗？
不会。 默认 cache: 'default' 对于普通脚本中的 fetch 请求，不会先查缓存，直接发网络请求。 只有导航请求（地址栏回车）或请求带条件头（If-None-Match）时，才会利用 HTTP 缓存。
Q: 如何让 fetch 先检查缓存，没有再发请求？
目前 fetch API 没有 "先检查，发现过期才请求" 的单一选项。 force-cache 会优先用缓存（但不验证是否过期）。 要实现"缓存优先，过期再请求"，需要配合 Cache API 或 Service Worker。
Q: no-cache 和 no-store 到底有什么区别？
no-cache：请求时强制发验证（带 If-None-Match），如果服务器返回 304 就用缓存。 no-store：完全不看缓存、不存缓存，每次都是全新请求。
Q: force-cache 会返回过期数据吗？
会。 当缓存命中但不新鲜（过期）时，force-cache 直接返回缓存， 不会向服务器验证。如果你的数据频繁变化，用 force-cache 可能导致用户看到过期内容。
Q: only-if-cached 有什么用？
主要在 Service Worker 中实现离线优先策略。 当用户离线时，用 only-if-cached 可以避免发起真实网络请求， 直接从缓存返回数据，未命中则返回网络错误。
Q: POST 请求会被缓存吗？
默认不会。HTTP 规范不建议缓存 POST 请求。 如果需要手动缓存 POST 响应，可以通过 Cache API 或在 Service Worker 中拦截并存储。
Q: fetch 的 cache 选项和 HTTP 缓存是一回事吗？
不是完全相同。HTTP 缓存：浏览器对 HTTP 响应的存储，受 Cache-Control、ETag 等 HTTP 头控制。 fetch cache 选项：控制 fetch 请求如何与 HTTP 缓存交互。两层层叠，共同决定最终行为。
