🔐 乐观锁与悲观锁

并发控制的核心机制 - 交互式学习演示

📋 核心概念对比

悲观锁 vs 乐观锁

维度 悲观锁 乐观锁
策略 先加锁，后操作 先操作，后验证
实现 数据库锁/分布式锁 版本号/CAS
冲突处理 阻塞等待 失败重试
性能特征 冲突多时性能低 冲突少时性能高
适用场景 写多读少 读多写少
死锁风险 有风险 无

🔄 工作流程图解

悲观锁流程

① 获取锁
→
② 操作数据
→
③ 释放锁
→
④ 完成

其他线程在①阶段阻塞等待，直到锁释放

乐观锁流程

① 读取数据
记录版本号
→
② 业务计算
→
③ 更新时
验证版本
→
④ 成功/重试

版本匹配则成功，不匹配则重试（无阻塞）

开始 │ ├─ 并发量大、冲突频繁？ │ ├─ 是 ──→ 悲观锁 │ └─ 否 │ │ │ ├─ 事务时间长？ │ │ ├─ 是 ──→ 乐观锁 │ │ └─ 否 │ │ │ │ │ └─ 写多还是读多？ │ │ ├─ 写多 ──→ 悲观锁 │ │ └─ 读多 ──→ 乐观锁

⚡ 版本号机制

数据库更新语句

-- 表结构需要包含 version 字段 CREATE TABLE products ( id BIGINT PRIMARY KEY, name VARCHAR(100), stock INT, version INT DEFAULT 0 ); -- 关键：UPDATE 时检查 version UPDATE products SET stock = stock - 1, version = version + 1 WHERE id = 1 AND version = 1; -- ← 乐观锁核心：版本匹配才更新 -- 影响行数为 0 时表示版本冲突，需要重试

Java CAS 实现

import java.util.concurrent.atomic.AtomicReference; public class AtomicStock { private final AtomicReference stock = new AtomicReference<>(100); public boolean deduct(int quantity) { while (true) { Integer current = stock.get(); if (current < quantity) { return false; // 库存不足 } // CAS：只有 current 没变时才更新成功 if (stock.compareAndSet(current, current - quantity)) { return true; // 扣减成功 } // 否则 current 已被其他线程修改，自旋重试 } } }

⚠️ 常见问题

1. ABA 问题

线程 A 读取数据为 A，线程 B 改为 B，线程 C 又改回 A。线程 A 看到的仍是 A，误以为数据没变。

时间线: T1: 线程A读取 → A T2: 线程B修改 → B T3: 线程C修改 → A // 变回来了！ T4: 线程A CAS → 成功 // 但中间被改过

✓ 解决方案：版本号机制

即使值相同，版本号也不同。CAS 时同时检查值和版本号。

// 只有 值 AND 版本号 都匹配时才更新 if (value == expectedValue && version == expectedVersion) { // 更新成功，version++ }

2. 重试风暴

高并发下大量请求同时版本冲突，触发重试，可能加剧系统负载。

✓ 解决方案：指数退避 + 随机化

// 指数退避重试 for (int i = 0; i < maxRetries; i++) { try { return operation.get(); } catch (OptimisticLockException e) { long backoff = (long) Math.pow(2, i) * 100; // 100, 200, 400ms... int jitter = random.nextInt(100); // 添加随机抖动 Thread.sleep(backoff + jitter); } }

3. 分布式环境

单机 CAS 在分布式环境中无效，需要分布式锁协调多台机器。

✓ 解决方案：Redis 分布式锁

// 使用 Redisson RLock lock = redisson.getLock(lockKey); boolean acquired = lock.tryLock(10, 30, TimeUnit.SECONDS); try { if (acquired) { task.run(); } } finally { if (acquired && lock.isHeldByCurrentThread()) { lock.unlock(); } }

4. 死锁预防

多把锁无序获取时，可能形成循环等待，产生死锁。

✓ 解决方案：固定加锁顺序 + 锁超时

// 方案1：固定顺序（按 ID 大小） Account first = from.getId() < to.getId() ? from : to; Account second = from.getId() < to.getId() ? to : from; synchronized (first) { synchronized (second) { // 转账操作 } } // 方案2：锁超时 boolean acquired = lock.tryLock(5, 30, TimeUnit.SECONDS); if (!acquired) { throw new LockTimeoutException("获取锁超时"); }
