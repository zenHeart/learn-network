理解并发控制的两种核心策略：通过可视化动画、代码示例和动手实验

💡 核心概念

🔴 悲观锁

"先加锁再操作" — 悲观的认为数据一定会被并发修改

  • 冲突处理：阻塞等待
  • 适用：冲突频繁场景

🔵 乐观锁

"先操作后检查" — 乐观的认为冲突很少见

  • 冲突处理：版本检测 + 重试
  • 适用：冲突较少场景

📊 典型场景

💰 金融余额扣减 悲观锁

一致性要求极高，扣成负数后果严重

📦 电商库存 混合

高并发秒杀，乐观锁优先+悲观锁兜底

👤 用户资料更新 乐观锁

各自修改自己的数据，冲突概率极低

🎫 座位预订 悲观锁

超卖后果严重，SELECT FOR UPDATE

🔴 悲观锁实现方式

1. 数据库行锁

SELECT balance FROM accounts WHERE user_id = 1 FOR UPDATE; -- 其他事务读取/修改同一行会被阻塞

2. Redis 分布式锁

const lock = await redis.set('order:lock:1', uuid, 'NX', 'PX', 30000); if (lock === 'OK') { try { /* 业务操作 */ } finally { await redis.eval(unlockScript, 1, lockKey, uuid); } }

3. 死锁避免：统一加锁顺序

// ✅ 正确：统一按 ID 大小排序 Long first = Math.min(fromId, toId); Long second = Math.max(fromId, toId); lock(first); lock(second);

⏱️ 悲观锁时序

TX-A (🔴) TX-B (🟡) ──────────────────────────────────────────────────── START │ ├─ SELECT ... FOR UPDATE 🔒 │ │ START │ ├─ SELECT ... FOR UPDATE │ │ └─ ⏳ 等待锁... │ ├─ UPDATE balance ├─ COMMIT 🔓 │ │ │ 🔒 获取锁 │ ├─ SELECT (读取TX-A更新后的值) │ ├─ UPDATE │ └─ COMMIT

🔵 乐观锁实现方式

1. 版本号机制

-- 读取: SELECT balance, version FROM accounts WHERE id=1; -- 返回: balance=1000, version=5 UPDATE accounts SET balance = balance - 100, version = version + 1 WHERE id = 1 AND version = 5; -- rows=1 → 成功 | rows=0 → 冲突!

2. CAS — CPU 级别无锁

int current; do { current = get(); } while (!compareAndSet(current, current + 1)); // CAS 失败则循环重试

⏱️ 乐观锁时序

TX-A (🔵) TX-B (🟢) ──────────────────────────────────────────────────── START │ ├─ SELECT bal=1000, v=5 │ │ START │ ├─ SELECT bal=1000, v=5 │ ├─ UPDATE ... WHERE v=5 → ✓ 成功(v=6) ├─ COMMIT │ │ ├─ UPDATE ... WHERE v=5 → ✗ 失败!(v=6) │ │ ⚠️ 乐观锁冲突! │ ├─ 重读: SELECT bal=900, v=6 │ ├─ UPDATE ... WHERE v=6 → ✓ 成功 │ └─ COMMIT

⚠️ 常见问题

问题描述解决方案
❗ ABA 问题A→B→A，CAS通过但实际被改过版本号扩展CAS
⚠️ 重试风暴热点行大量并发重试限流 + 退避策略
⚠️ 无界重试冲突持续时无限循环最大重试次数

🌲 选型决策树

❓ 问题：冲突频率高吗？

否 → 冲突少，优先乐观锁

是 → 继续判断...

❓ 一致性要求高吗？

是 → 必须精确 → 悲观锁

否 → 最终一致 → 混合方案

📌 快速决策

场景推荐
余额扣减、金融交易悲观锁
库存秒杀（高并发）混合 乐观锁优先 + 悲观锁兜底
用户资料更新乐观锁
座位/资源预订悲观锁
配置读取乐观锁
