执行顺序规则

规则说明
1. Task 优先每轮事件循环处理 一个 Macrotask
2. Microtasks 紧随每个 Task 后清空所有 Microtasks
3. rAF 适时执行Task + Microtasks 后触发（如果需要重绘）
4. Long Task 阻塞>50ms 的 Task 阻塞所有后续事件
5. Input 与 WS 同级都是 Task，没有内置优先级差异

为什么 Input 会"感觉"阻塞了 WS？

场景 1：同步长任务

Input handler 执行 heavyComputation()（500ms），WS 消息必须等待。

场景 2：alert() 模态框

alert() 完全暂停事件循环，WS 消息完全无法处理。

场景 3：大量微任务

Input handler 中 queueMicrotask() 填满微任务队列。

场景 4：Compositor 优先级

Linux 上 input 快速路径可能优先派发到 Task Queue。

关键观察：当你在输入框输入或点击「模拟 Long Task」按钮时，WS 消息的处理会被延迟。 这是因为同步代码占用了主线程，导致 Task Queue 中的后续任务（包括 WS 消息处理）无法执行。

解决方案对比

1. requestAnimationFrame

input.addEventListener('input', () => {
  requestAnimationFrame(() => {
    processInput(value); // 异步处理
  });
});

将处理推迟到下一帧，不阻塞当前 Task

2. requestIdleCallback

input.addEventListener('input', () => {
  requestIdleCallback(() => {
    processInput(value); // 空闲时处理
  }, { timeout: 1000 });
});

在浏览器空闲时处理，适合非紧急任务

3. Web Worker

const worker = new Worker('worker.js');
input.addEventListener('input', () => {
  worker.postMessage(value); // 计算移到 Worker
});

计算密集任务在 Worker 中执行，不影响主线程

4. 防抖 / 节流

import { debounce } from 'lodash-es';
const handleInput = debounce((v) => {
  ws.send(v); // 节流发送
}, 300);
input.addEventListener('input', (e) => {
  handleInput(e.target.value);
});

减少事件触发频率，降低主线程负载

方案选择指南

场景推荐方案
UI 即时反馈（输入验证）requestAnimationFrame
非紧急数据处理（分析、统计）requestIdleCallback
计算密集任务（JSON 解析、加密）Web Worker
减少网络请求（搜索建议）debounce / throttle
高优先级 WS 消息scheduler.postTask()（如支持）
⚠️ alert()/confirm() 无法规避：模态对话框会完全暂停事件循环，这是浏览器内置行为。 解决方案：使用自定义 Modal（如 SweetAlert）替代原生 alert()。
